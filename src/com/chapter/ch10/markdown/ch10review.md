### 전이 의존
* application 프로젝트
* A 모듈
* B 모듈

```
A 모듈이 B 모듈을 requires 하고 있다고 가정,
application 프로젝트에서 A 모듈을 requires 하여 사용하고 할 때,
B 모듈까지 사용하고자 한다면 A 모듈에 requires 되어 있는 B모듈에 transitive 키워드를 선언해 주면 된다.

* transitive 키워드: 모듈을 사용하는 다른 모듈에게 자동으로 접근 권한을 부여함
```


### 리플렉션
* 은닉된 패키지는 기본적으로 다른 모듈에 의해 리플렉션을 허용하지 않는다.
* 리플렉션이란? 
    * 실행 도중에 타입(클래스 ,인터페이스)을 검사하고 구성 멤버를 검사하는 것이다.
* 경우에 따라 은닉된 패키지도 리플렉션을 허용해야 할 때가 있다.
```
1. 모듈 전체 리플렉션 허용
open module 모듈명 {
}

2. 지정된 패키지에 대해 리플렉션 허용
module 모둘명 {
    opens 패키지1;
    opens 패키지2;
}

3. 지정된 패키지에 대해 특정 외부 모듈에서만 리플렉션 허용
module 모듈명 {
    opens 패키지1 to 외부모듈명, 외부모듈명, ...;
    opens 패키지2 to 외부모듈명;
}

[ open, opens 키워드로 리플렉션을 허용할 수 있다는 점만 알고 넘어가기. ]
```
* export는 다른 모듈이 패키지의 public 타입을 사용할 수 있도록 허용하는 반면, opens는 리플렉션을 통한 모든 타입의 접근을 명시적으로 허용한다.

### 자바 표준 모듈
* JDK가 제공하는 표준 라이브러리: 자바 프로그램이라면 반드시 활용
* 표준 라이브러리는 Java 9 부터 모듈화가 되어 Java 17 표준 모듈이 완성되었다.
* java.base는 모든 모듈이 의존하는 기본 모듈이다.
* java.base 모듈은 requires 하지 않아도 사용할 수 있지만, 다른 모듈들은 모듈 기술자에 requires를 명시하고 사용해야 한다.
* java.base 모듈(java.lang, java.util, java.io 등 핵심 패키지 존재, java.lang을 제외하고 import 하여 사용 가능) 
* java.se는 JDK가 제공하는 모든 모듈을 제공하는 집합 모듈이다.(Java 8 이전 버전과 같이 자바 표준 라이브러리를 제한 없이 사용하고 싶을 경우에는 이 java.se를 requires하면 된다.)
* 또 다른 방법은 모듈 기술자가 없는 프로젝트를 생성하는 것
* 모듈 기술자가 없으면 모듈로 인식되지 않기 때문에 자바 표준 라이브러리를 제한 없이 사용할 수 있다.

자바 8 이전까지는 응용프로그램이 표준 라이브러리의 5%만 사용하는데 불구하고 응용프로그램을 실행하려면 전체 표준 라이브러리가 갖추어진 자바 실행 환경(JRE)이 필요했었다.
*  표준 라이브러리를 모듈화한 이유는 응용프로그램을 실행하는데 필요한 모듈만으로 구성된 작은 사이즈와 자바 실행 환경(JRE)을 만들기 위해서이다.
* 독립 실행형(응용프로그램 + 표준 라이브러리)으로 배포할 경우 표준 라이브러리의 크기가 작을수록 배포 사이즈가 줄어든다.
* 제한된 지원만 가지고 있는 소형(임베디드) 기기에는 사이즈가 작은 자바 실행 환경이 필요하다.

```
결론적으로, 자바의 표준 라이브러리가 모듈화되어 애플리케이션 개발과 배포를 더 효율적이고 유연하게 만들었다는 것을 전달한다.
모듈화를 통해 개발자는 필요한 부분만을 선택하여 사용할 수 있게 되었고, 이는 애플리케이션의 크기를 줄이며, 특히 제한된 리소스를 가진 환경에서의 실행 효율성을 높일 수 있게 한다.

개발적 관점에서 정의하자면, 자바 표준 모듈 시스템은 JDK 9 부터 도입되어 자바 애플리케이션의 구조와 배포 방식을 혁신적으로 개선한 기술이다.

이 모듈 시스템은 자바 플랫폼 자체와 개발자가 작성하는 애플리케이션 모두에 대해 더 세밀한 의존성 관리와 캡슐화를 가능하게 한다.
자바 17까지 이 모듈화 작업은 지속적으로 발전되었으며, 이를 통해 애플리케이션은 필요한 부분만을 포함하여 더 작고, 더 효율적인 실행 환경을 구성할 수 있게 되었다.
```
